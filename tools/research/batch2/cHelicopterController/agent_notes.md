
## cHelicopterController batch 2 findings (VEHICLE_CONTROL/cHelicopterController.cpp; 17 of 80 candidates exact, 21 of the 28 candidates F26-F48/F52/F79/F80 that were attempted)

- **Split.** The window starts inside another class: F01-F25 are `cVehicleController`'s file (its ctor F09 0x82781B38 is the out-of-line base ctor of the helicopter; dtor F10 is slot 0 of the helicopter vtable; F11/F19 are its "type id" accessors, F12-F16 state setters). The helicopter file begins at F26 (the prototype's `MakeNew`). F52 (`??_G` of the *prototype*) is also this file. F53-F55 are another class (vptr 0x8214C264, Havok `removeEntity`), F50 a vector helper; F49-F71 were not analysed in depth (VMX-heavy). Hot-region F72-F78 are shared base-class stubs, not this file's.
- **Prototype class without a 2nd-base vptr store.** `MakeNew` (F26) stores exactly two vptrs (0 and 0x18) after an out-of-line base ctor. A second base with a plain vtable gave a THIRD, dead store (0x18 stored twice). Declaring the polymorphic second base `__declspec(novtable)` removes its constructor-time vptr store and gives the exact code. Probably the real second base is an abstract interface.
- **Calling the grandparent's virtual qualified.** F34 (slot 6) calls the ROOT base's version (`cVCRoot::GetControllerType()`, result discarded into a 16-byte stack temp) and then returns a global id by hidden pointer. Both must return the same 16-byte struct (`tControllerType`; CD2 only writes the first word), otherwise the override is not legal C++. A struct with a user constructor is returned through the hidden pointer with RVO; one without gets copied via temporaries.
- **Size of a helper's return struct changes the frame.** In F33 the helper `QueryType(int)` returns a 4-byte non-POD (`tTypeKey` with a user ctor): returning a 16-byte struct made the frame 0x90 instead of 0x80. Match the helper's return type SIZE, not just its shape. `int cur = g_global; if (cur != Q(..).m_nType) return T(other); return T(g_global);` yields the early load into a callee-saved register, the reload in the equal arm, and the "other" arm first.
- **Evaluation order of `global == f()`.** MSVC evaluates the call first and loads the global after it. To load the global BEFORE the call (target: `lwz r29, global` then `bl`), copy it to a local first.
- **Positive modulo (F42).** `i = idx % n; if (i < 0) i += n;` with `n` a local copy gives `add r10,r10,r11`; the target's `add r10,r11,r10` came from re-reading the field: `if (i < 0) i += m_nCount;`. Arm order `if (m_nCount == 0) p = first; else {...}` gives the target's `cmplwi/bne` layout; `int n = m_nCount; if (n)` gives `cmpwi/beq`.
- **Vector wrap (F48)**: `i = idx; if (idx < 0) i = size() + idx; if (idx >= size()) i -= size();` with an inline `size()` (`(end-begin)`, `srawi 4`, computed three times).
- **RVO of a forwarded virtual (F47).** `return p->sub.Virtual();` forwards the hidden return pointer (r3 untouched) only when the return type is a class with a constructor (`Fun_Runtime::Vec3`, align 16); a plain 4-float POD goes through a temp and is copied.
- **Template helpers need `inline`** under /Ob1: an un-inlined `Clamp(const T&, const T&, const T&)` stays a call. CD2 inlined it with reference semantics: the result is `&hi` (the global itself, `addi r11, base, off`) when `v > hi`, a stack temp (`-lim` or `v`) otherwise.
- **fmadds operand choice (F46, open).** Naming a temp for one of the squares stops the fusion (`fadds`). The target loads `in[2]` before `in[0]` yet its plain `fmuls` is `x*x`; in ours the plain `fmuls` is on the first-loaded value. Not reproduced. F45 (cross product) has the same kind of open operand-order difference.
- **Constructor under LTCG (F36).** All 36 stores match the target in order (vptrs 0/0x18/0x1C/0x30/0x38, Vec3 zeroing, then the body order `0x7D, 0x7C, 0x848, 0x88D, 0x840, 0x88C, 0x84C, 0x88E, ...`). The target loads its float constants through TWO anchor registers (`flt_820F7F30`, `flt_820EAA48`, mixed with direct `lis/lfs`); the harness's LTCG model registers five direct constants and one pool, so it gets 3/79 words. Not counted exact.
- **Harness quirk.** F28 (`b ctor` tail call) and F80 (atexit) are exact in the plain build but show "0/6" and "3/3 words" under `--ltcg` (tail target placement in the LTCG image); counted as plain-exact.
- **Layout.** Helicopter fields start at 0x840 (CD2's `cVehicleController` is 0x840 bytes, RuffKing's 0x870). Flags 0x7C/0x7D and vehicle pointers 0x88/0x94 live in the base. The five vptrs 0, 0x18, 0x1C, 0x30, 0x38 are reproduced with five stand-in polymorphic bases. The `cVehicle` stand-in has an interface at +0x30 (slot 1 = `IsKindOf(tag)`) and a physics pointer at +0x1948 (max speed at +0x368).
- **Unreproduced (F37, F38).** Two near-identical state transitions: they inline a container accessor three times (`front()` of an intrusive list at vehicle+0x1180 with sentinel at +0x10, then `node->0x40 - 0x1C`), a virtual type test on the +0x30 subobject, a state compare `== 3` and a mode switch 1 -> 2 (F37, flag 0x88C) or 2 -> 1 (F38, flag 0x88D). Needs the real list/iterator types.
